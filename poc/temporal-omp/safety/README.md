# Safety receipt and Git effect reconciliation probe

This standalone package has no runtime dependencies. It does not require Temporal or OMP and does not establish their runtime recovery guarantees.

## Run

From the repository root:

```sh
node poc/temporal-omp/safety/scenario.ts
```

Or run `npm run probe` from this directory. Node must support TypeScript type stripping (Node >=22.19). The runner creates an isolated repository and local bare remote under the system temporary directory; it does not use the enclosing repository's Git configuration, remote or worktree. It retains a sanitized machine-readable report at `evidence/latest.json`. Temporary repositories remain available for inspection; no credentials or raw agent sessions are collected.

The actual run exited successfully and recorded 19 behavioral observations: a worker committed and pushed to the local bare remote, exited 73 before returning any receipt, and recovery read local/remote Git state without repeating the claimed operation. Dirty local state, subsequent committed/pushed state and an unavailable remote all blocked recovery. Receipt cases reject malformed JSON, status/schema mismatch, independently unproven completion, incorrect SHA, every binding field mismatch, mismatched observer binding and stale-generation results. A higher generation prevented a stale owner from dispatching a new effect.

## Typed exports (`index.ts`)

- `Binding`: `{mandateId,itemId,stage,attempt,revision,generation}`. Attempt/generation are positive safe integers; revision is a lowercase SHA-1 Git commit ID (40 hexadecimal characters).
- `GitIntent`, `GitEvidence`, `Receipt`, `ValidationResult`, `Reconciliation`: standalone contracts.
- `isBinding(value)` and `bindingKey(binding)`: strict binding schema and stable tuple identity.
- `validateReceipt(raw, expected, evidence, currentGeneration)`: accepts an object or JSON string; returns `{accepted:true,receipt}` or `{accepted:false,reason}`. The schema is exact, including nested structures. A completed status is necessary but never sufficient. The agent's boolean `completion` is intentionally ignored: `false` with actual independent proof passes, `true` without proof fails.
- `observeGitEffect(intent)`: synchronously reads commit existence, HEAD, branch, working-tree cleanliness and exact remote ref using Git. Throws on unavailable/unresolvable state.
- `reconcileGitEffect(intent)`: read-only classification, either `observed-complete` with evidence or `blocked`; never commits, pushes, resets or replays anything.
- `claimEffect(stateDir,effectKey)`: exclusive persistent dispatch marker. The key must identify the logical effect across attempts/generations; do not include changing attempt/generation fields when these represent the same external action.
- `runClaimedEffect(stateDir,effectKey,guard,operation)`: guards before claim, before dispatch and after operation. An existing claim returns `unknown` without invoking operation. A failure after claim leaves the claim intact.
- `takeGenerationFence(stateDir,generation)`: returns a synchronous stale-generation guard; a higher token supersedes the older guard.

## Trust boundary and integration

The receipt is untrusted. The expected binding and Git intent come from the orchestrator, not agent output. Independent evidence must be generated by a trusted observer using the expected intent and passed separately; this module does not make an arbitrary supplied JSON evidence object authentic. `currentGeneration` must come from the authoritative owner registry. An integration must atomically check ownership and commit acceptance in that authority; passing an old generation snapshot does not provide transactional fencing. Remote/repository paths are trusted local configuration, not arbitrary agent command arguments.

For the lost-result scenario, the worker persists the intended commit ID after the real commit, pushes, and terminates before writing a completion receipt. The retained intent is not proof; independent recovery queries Git. A missing claim, an absent intended revision or unresolved state must not be interpreted as permission to repeat a previously unknown action. The scenario intentionally preserves dispatch markers across retries.

## Explicit limits

This is a single-host, local-filesystem behavioral probe, not deployment or distributed consensus. Generation checks cannot stop an already-dispatched external command and have a check-to-dispatch race. Git evidence is point-in-time and can become stale immediately afterward. A local bare remote is not GitHub. Exclusive-file claims are not a power-loss durability guarantee (no fsync protocol). The worker's explicit exit after push is result loss, not a Temporal/OMP crash or machine power loss. No Temporal server replay, OMP session continuity, cross-host takeover or runtime crash was exercised. No full build, typecheck, lint or test suite was run.
